Every key tap counts, at every frame rate

The game reads each button once per frame, so a key tap or a short key release between two reads is lost. The branch latches each key press between two reads. Scope change, 2026-11-23: keyboard only. The pad stays at one read per frame, and the game targets at least 60 FPS.

In play: fast key taps and mashed keys count at 30 FPS as at 60 FPS. A sub-frame tap is one frame of press. The pad does not change.

A tap gives JUST_PRESSED, then JUST_RELEASED. A short release gives JUST_RELEASED, then JUST_PRESSED. The control lock ignores the latch.

Decisions

Keyboard only; the pad thread is dropped

Chosen Keyboard latch only. SDL2 and Jamepad are not safe from a second thread, and no drop-in Java pad library (input4j, sdl2gdx) keeps sub-frame taps. Pad events through LWJGL 3.4 and SDL 3 become a backlog candidate. The earlier questions D4 to D6 are void.

Risks

Low risk: no thread, no new device code

  • risk Keyboard and pad on one button. A new key press while the pad holds the same button gives a short release. It needs both devices on one button at once.
  • risk Menus. A key tap now always gives one press in the menus too. A play check covers it.
