One falling-piece entity

DebrisPiece, BlockPiece and WoodCratePiece share the same body, life and draw order; they differ in 7 values. One FallingPiece with a typed def per kind replaces the 3 classes, so a new kind of piece needs no new class.

In play: nothing changes. Robot debris, broken blocks and crate splinters fly, fall, spin and blink as before.

Before and after

Three classes become one class and three defs

Code sketch

A caller names its kind

Today, WoodCrate:

MegaEntityFactory.fetch(WoodCratePiece::class)!!.spawn(props(POSITION pairTo p, IMPULSE pairTo v, ...))

After:

FallingPiece.spawn(FallingPieceDef.WOOD_CRATE, key, position, velocity)

enum class FallingPieceDef(val gravity: Float, val fallClamp: Float?, val frictionX: Boolean,
    val jitter: Float, val size: PieceSize, val spin: Spin?, val blink: Float?) {
    DEBRIS(...), BLOCK(...), WOOD_CRATE(...)
}

Decisions

Three decisions

No map spawns a piece; only code does. The 3 classes share one pool after the change, so a reused piece can change kind.

D1 Chosen Typed def; per-value properties override it (or replace it, when all 7 are given).

D2 Chosen Region keys and one cache in the piece.

D3 Chosen Reset the spin angle at spawn.

Risks

One pool for three kinds

  • risk A reused piece keeps a field of its last kind. Each spawn and frame sets every field a kind can change; a test and a new test room that spawns all 3 kinds check it.
  • risk Motion changes. A temporary side-by-side suite runs frozen copies of the old 3 classes against the new class with a fixed seed; it is deleted before the merge.
  • risk Text conflicts with 060c (imports in 7 caller files) and 139a (one test rig line).
