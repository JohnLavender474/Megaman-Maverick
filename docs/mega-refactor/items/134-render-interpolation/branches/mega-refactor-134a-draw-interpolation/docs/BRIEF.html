Draw interpolation

At 60 fps the world runs 2, then 3, then 2 steps of 1/150 s per frame, so bodies and the view move by ±20 % from frame to frame. This branch draws each body and the camera between its last 2 step positions, by the leftover time of the step clock. The physics does not change.

In playWith --interpolation true: the level scrolls evenly, and Megaman and X do not pulse against the view. With the default (false): nothing changes.

Collisions, timers, spawns, culling, edge blocks and the gameplay camera keep the step positions. Only the draw reads the offsets.

Decisions answered 2026-11-09

D1

Distance guard for jumps inside a step?

A teleport inside a step (a hook that moves the body) would be drawn as a slide for 1 frame. A guard sets the offset to 0 when one step moves a body more than a limit. The fastest normal move is a fall at 8.5 px per step.

ChosenGuard at 1 tile per step32 px: about 4 times the fastest normal move. Catches the teleports without an audit of all body hooks. Explicit snaps come in 134b.
Guard at half a tileCatches smaller jumps, but is nearer to fast normal moves.
No guardExplicit snaps only, all in 134b. Streaks with the flag on until then.
D2

Co-op shared view: what draw offset?

The shared focus averages the players and eases when the group changes. Its position read changes its ease state, so the draw needs its own read.

ChosenAverage of the grouped players0 while the ease or a view-edge keeper acts. The shared view is even in normal play.
0 in co-opThe co-op view stays stepped. The players shake against it until a later branch.
D3

How to compare on and off?

The judder is easiest to see when you switch in the same room and keep moving.

ChosenLaunch flag plus a dev key--interpolation sets the start value. A keyboard dev key switches it live, only in a dev run. (Corrected 2026-11-09: the key is I, armed only when the launch gives --interpolation, like the screenshot key P.)
Launch flag onlyFewer parts. Each compare needs 2 launches.

Risks

  • Attached bodies jitter with the flag on. A body that follows another body outside the steps (riders, boss parts) is drawn up to one step away from its parent. This is the 134b audit. The flag stays off until then.
  • The draw lags by up to one step. 6.7 ms at MEDIUM, 3.3 ms mean. The play test compares the input feel with the A/B switch.
  • Cost on weak machines. 2 field writes per body per step, 1 lookup per sprite entity per frame, no allocation. The diagnostics runs measure WorldSystem and SpritesSystem with the flag off and on.

Scope change owner, 2026-11-09

The draw offset is no longer on IFocusable, and the room subject is split from it. Each camera part reads only what it needs: IFocusable.getFocusPosition() (the follow target), IRoomSubject.getSubjectBounds() (the rooms and the start of a transition), and IDrawOffsetSource (the draw camera). MegaLevelScreen sets all 3 in one place. No behavior change: the rooms still follow slot 0, and the view follows the group.

Scope change 2 owner, 2026-11-09

Interpolation is on by default (--interpolation false turns it off). The known 134b items (attached bodies, sprite entities with no body, small teleports, the shape renderer) now show in normal play; each has a TODO at its code. The play test adds checks in real levels with those entities.

Scope change 3 owner, 2026-11-09

CameraRoomBounds, CameraLimitStage, CameraDrawOffset and IDrawOffsetSource moved to engine. CameraSubject is now an engine mechanism (set(target, room, draw)); the core PlayersCameraSubject holds the game's policy (the rooms follow slot 0). This overlaps item 130.
