One seeded random source

Every random value comes from one session seed, through services.random. A test or a later replay can then fix the seed or script the values.

In play: Nothing changes. The ranges stay the same; the start log shows the seed.

Before and after

Four unseeded sources become one seeded source

Code sketch

A call site names its stream

Today, AbstractEnemy (item drop) and a debris spawn:

val roll = getRandom(0, 100)
val pos = bounds.getRandomPositionInBounds(out)

After (with D1 a):

val roll = services.random.nextInt(0, 100)
val pos = bounds.getRandomPositionInBounds(services.random, out)

Tests script the values in place of UtilMethods.random.setSeed:

val services = testServices(random = SeededRandom(seed = 42L))

Decisions

Four decisions

About 230 random lines in 80 files change. D1 sets how they reach the source.

D1 Chosen Inject services.random; delete UtilMethods.random and getRandom*.

D2 Chosen One stream. changed 2026-11-14 The diagram and sketch now show one source.

D3 Chosen A clock seed per run, logged, and --randSeed <long>.

D4 Chosen A core source-scan test.

Risks

An off-by-one bound is the main risk

  • risk Range bounds. Old calls mix inclusive and exclusive bounds. The new API names the inclusive bound; unit tests pin each range.
  • risk D-1000 test seeds. Two tests search for a seed with the java.util.Random algorithm. The seeded stream stays on java.util.Random; a changed draw order changes their search.
  • risk Overlap with 024a. Both branches change the Moon Scythe sort line in the weapons handler.
