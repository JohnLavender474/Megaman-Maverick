Level reset event

24 entity classes listen to PLAYER_SPAWN, but each one uses it to mean "the level was reset". The respawn routine now sends that fact itself, as LEVEL_RESET, from its reset step. A player's spawn no longer resets the level as a side effect.

In playNothing changes. The new event arrives in the same events.run(), to the same listeners, in the same order.

The level reset depends on slot 0 spawning. Slot 1 sends nothing, because a second event would reset the level twice. A TODO in playerSpawnEnd() names this item.

Decisions answered 2026-11-06: as recommended

D1

What happens to PLAYER_SPAWN?

After the move, no code listens to it. The item decision (2026-10-23) said "a spawn event for each player". The rule O1-R5 says no code without a production caller.

ChosenRemove itDelete the event, its submit and the slot-0 TODO. Co-op (047) adds a spawn event for each slot when a listener needs one.
Keep it, for each slotEvery slot sends it on spawn. It matches the item text, but nothing listens to it yet.

Nothing else needs a decision. The name LEVEL_RESET and the sender (the routine) come from the 038a brief.

Risks

  • A missed listener. It would stop culling or resetting on a respawn. With D1 as recommended, the event goes, so a missed use does not compile.
  • Frame timing. The submit moves earlier in the same frame. A test checks that LEVEL_RESET arrives once, in the frame of the reset, at a menu start, a launch start and a respawn, and not on game over.
  • Overlap with 081b. Its X player calls the same playerSpawnEnd(), so it gets the change through the shared function.
